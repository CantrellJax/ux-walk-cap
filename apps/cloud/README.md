# Cap UX sharing server

A standalone Cloudflare Worker, private R2 bucket, D1 database and static viewer. No Cap account, billing API, subscription or upstream web application is required. The server runs in self-hosted owner mode with one upload credential, and can additionally host user accounts (Better Auth: passkeys, GitHub and Google sign-in, and a device flow for the desktop app and CLI). Account signup stays closed until `SIGNUP_ENABLED` is set to `true`.

## Deploy your own

Use Node 22 or newer and your own Cloudflare account. The Jacks Unlimited instance is `capux.jaxtrell.workers.dev`; its resources are isolated from onCall.

```sh
cd apps/cloud
npm ci --ignore-scripts
npm run check
export CLOUDFLARE_ACCOUNT_ID=YOUR_ACCOUNT_ID
npx wrangler whoami
npx wrangler r2 bucket create capux-media --update-config=false
npx wrangler r2 bucket lifecycle add capux-media capux-retention '' --expire-days 31 --abort-multipart-days 1 --force
npx wrangler d1 create capux-accounts
npx wrangler d1 migrations apply capux-accounts --remote
npm run deploy
npx wrangler secret put UPLOAD_TOKEN
```

`wrangler d1 create` prints a `database_id`; add it to the `DB` entry under `d1_databases` in `wrangler.jsonc` before applying migrations. Apply migrations before every deploy that adds one; the Worker stores share ownership and usage in D1 in both owner and account modes. The two `ratelimits` bindings need no separate resource: their `namespace_id` values are arbitrary integers unique within your account.

At the secret prompt, supply a randomly generated credential of at least 32 characters. Save the same credential in Cap UX Settings → Sharing. Keep it in your password manager or system credential store; do not paste it into source, a recording, a URL or an issue. Requests to create shares return 503 until the secret is configured. Rotate it with the same secret command; existing links remain revocable with the new owner credential.

Change the Worker and bucket names in `wrangler.jsonc` for another instance. Set the deployment's returned HTTPS origin in the app. A custom domain can route to this same Worker later; API and viewer must share an origin so scoped playback cookies work. Never make the R2 bucket public. The 31-day retention rule applies only to this sharing bucket; it leaves source recordings on the user's computer untouched.

### Enabling accounts

Accounts stay off until `BETTER_AUTH_SECRET` is set; owner mode works without them.

1. Set `BETTER_AUTH_URL` in `wrangler.jsonc` to the deployment's HTTPS origin (no trailing slash). Passkeys are bound to that hostname, so pick the long-term origin, such as a custom domain, before users register passkeys.
2. Create OAuth apps. GitHub: authorization callback `https://YOUR_ORIGIN/api/auth/callback/github`. Google (OAuth client, web application): authorized redirect URI `https://YOUR_ORIGIN/api/auth/callback/google`. A provider is enabled only when both its id and secret are present.
3. Store the secrets:

```sh
npx wrangler secret put BETTER_AUTH_SECRET
npx wrangler secret put GITHUB_CLIENT_ID
npx wrangler secret put GITHUB_CLIENT_SECRET
npx wrangler secret put GOOGLE_CLIENT_ID
npx wrangler secret put GOOGLE_CLIENT_SECRET
```

`BETTER_AUTH_SECRET` must be a random value of at least 32 characters (`npx auth secret` prints one); rotating it signs everyone out. Do not commit any of these values.

4. Leave `SIGNUP_ENABLED` as `"false"` until you are ready to accept new users. With it off, existing users can still sign in and owner mode is unaffected. `FREE_PLAN_MAX_BYTES` and `FREE_PLAN_MAX_SHARES` set the free plan's quota.

Users sign in at `/signin` with GitHub or Google; their first sign-in creates the account. They can then add a passkey on `/account` and use it for later sign-ins. `/account` also shows usage, exports account data and deletes the account. Native clients approve a device code at `/device`.

| Secret or variable | Kind | Purpose |
| --- | --- | --- |
| UPLOAD_TOKEN | secret | Owner upload credential (owner mode) |
| BETTER_AUTH_SECRET | secret | Signs sessions and cookies; enables accounts |
| GITHUB_CLIENT_ID, GITHUB_CLIENT_SECRET | secrets | GitHub sign-in |
| GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET | secrets | Google sign-in |
| BETTER_AUTH_URL | var | Public origin; also the passkey relying party |
| SIGNUP_ENABLED | var | `"true"` allows new accounts |
| FREE_PLAN_MAX_BYTES, FREE_PLAN_MAX_SHARES | vars | Free plan quota |

### Schema changes

The D1 schema lives in `migrations/`. `0001_better_auth.sql` is generated by the Better Auth CLI; do not edit it. After changing auth options or plugins, generate the next migration from the existing ones:

```sh
npm run auth:generate -- migrations/0003_describe_change.sql
```

`auth.config.ts` loads the committed migrations into an in-memory SQLite database so the CLI emits only the difference. Hand-written migrations (such as `0002_shares.sql`) cover the server's own tables.

For local simulation, use the same config without remote bindings and a local `.dev.vars` containing only synthetic values (UPLOAD_TOKEN, and BETTER_AUTH_SECRET plus `BETTER_AUTH_URL=http://localhost:8787` to try accounts). Apply migrations locally with `npx wrangler d1 migrations apply capux-accounts --local`. Tests run real workerd with ephemeral local R2, D1, rate limits and assets, and a mocked GitHub OAuth server; they do not call Cloudflare or upload personal recordings.

## Desktop and CLI

Sharing is off by default. Settings → Sharing controls the server, upload credential and expiry (1, 7 or 30 days). A recording's Share video action publishes only its finished video and copies the link. Studio recordings without an export need to be exported in the editor first. Screenshot Share publishes the composited PNG or JPEG. Revoke link stops access through that server; it does not delete the local recording.

```sh
cap sharing configure --server https://YOUR_WORKER.workers.dev --enable
cap sharing configure --token-stdin < /path/to/protected-credential
cap upload recording.mp4 --json
cap sharing status
cap sharing revoke SHARE_ID
```

Desktop and CLI read `~/.config/cap-ux/sharing.json`. Credentials are keyed by server origin in the system credential store. CAP_UX_UPLOAD_TOKEN supplies a headless credential; CAP_UX_SHARING_CONFIG selects an isolated configuration for testing. HTTPS is required except for localhost development. Redirects are refused so upload credentials cannot move to another endpoint. There is no Cap service fallback.

## Protocol v1

All JSON is bounded. Writes require `Authorization: Bearer <owner-upload-credential>`. All routes return private/no-store responses. No CORS grants are needed for the same-origin viewer or native client.

| Method and path | Result |
| --- | --- |
| GET /healthz | Product and protocol version |
| POST /api/v1/shares | Accept title, contentType, size and expiresInDays; return id, partSize, sharePath and expiresAt |
| PUT /api/v1/shares/ID/parts/N | Upload exactly the declared part size (final part can be smaller); return partNumber and etag |
| POST /api/v1/shares/ID/complete | Accept ordered parts; validate final size before publishing |
| DELETE /api/v1/shares/ID | Revoke access and remove the published media or abort an incomplete upload |
| GET /api/v1/shares/ID/metadata | Read title, size, content type and expiry with a read capability |
| GET or HEAD /api/v1/shares/ID/media | Authorized media; single byte ranges supported |
| POST /api/v1/shares/ID/access | Exchange the read capability for a scoped HttpOnly playback cookie bounded by link expiry |
| GET /s/ID#READ_CAPABILITY | Viewer; the fragment is exchanged for playback access and never sent in the HTTP URL |

The create response's link is not readable until completion. The viewer capability is distinct from the upload credential and stored as a hash. Possessing a viewing link never authorizes uploads or revocation. Revocation has an independent tombstone so a concurrent completion cannot restore access. Expiry is enforced on every read; the bucket lifecycle later removes stored objects. Clients verify the final media's size before reporting success, revoke incomplete/failed attempts, and keep local files.

Supported media: video/mp4, image/png and image/jpeg. Maximum media size: 20 GB. Multipart size: 8 MiB. Link expiry: 1–30 days. Raw traces, cookies, local configuration, API keys, notes and reports are not accepted as upload media.

## Protocol v2

Protocol v2 adds accounts without changing any v1 route or response. `/healthz` reports `protocol: 2`, whether accounts are enabled, whether signup is open, and the enabled sign-in providers.

### Principals

Every `/api/v1` write is made by a principal: the owner (`Authorization: Bearer <UPLOAD_TOKEN>`) or a signed-in user (`Authorization: Bearer <session token>` from the device flow, or the session cookie on same-origin pages). Cookie-authenticated writes must carry a matching `Origin`. Request bodies never choose an owner. A share belongs to the principal that created it, recorded in D1 and in the share's manifest; part uploads, completion and revocation by any other principal return 404, exactly like an unknown id. Viewing still requires the share's read capability; a session token is not a read capability. Recovery routes remain owner-only.

### Account routes

| Method and path | Result |
| --- | --- |
| GET /api/v1/me | `principal` (`owner` or `user`), `user` (id, email, name), `plan`, `usage` (storedBytes, activeShares) and `quota` (maxStoredBytes, maxActiveShares; null for the owner) |
| GET /api/v1/me/export | JSON download: user, and each share's id, title, type, size, status, timestamps and viewer URL. Read capabilities are stored only as hashes and cannot be exported |
| DELETE /api/v1/me | Users only: revoke every share, delete its media and manifest, then delete the user, sessions, linked accounts and passkeys. Requires a session created within the last day; otherwise `SESSION_EXPIRED` and the user signs in again |
| /api/auth/* | Better Auth endpoints (social sign-in and callbacks, passkeys, sessions, device flow, delete-user) |
| GET /signin, /device, /account | Same-origin pages |

### Device authorization (RFC 8628)

Allowed `client_id` values: `cap-ux-desktop` and `cap-ux-cli`.

1. `POST /api/auth/device/code` with `{"client_id": "cap-ux-cli"}` returns `device_code`, `user_code`, `verification_uri` (`/device`), `verification_uri_complete`, `expires_in` (600) and `interval` (5).
2. The client shows the code and opens `verification_uri_complete`. The signed-in user reviews the request at `/device` and approves or denies it.
3. The client polls `POST /api/auth/device/token` with `{"grant_type": "urn:ietf:params:oauth:grant-type:device_code", "device_code": "…", "client_id": "cap-ux-cli"}` no faster than `interval`. Errors follow RFC 8628: `authorization_pending`, `slow_down`, `access_denied`, `expired_token`.
4. Success returns `access_token` (`token_type: "Bearer"`, `expires_in`). Send it as `Authorization: Bearer` on `/api/v1` routes. Store it in the system credential store, as with the upload credential.

### Quotas, rate limits and error codes

Account writes are limited per plan. Every user has `plan: "free"` until a billing phase changes it. A share's declared size and the active share count are reserved atomically at create; a pending upload holds its reservation for at most a day. Completion re-checks the actual stored size; an upload that no longer fits is revoked and deleted.

| Status | `code` | Meaning |
| --- | --- | --- |
| 403 | `quota_exceeded` | The share would exceed the account's stored bytes or active shares |
| 429 | `rate_limited` | Too many share creations (30/min) or part uploads and completions (600/min) for this account |
| 403 | `not_an_account` | DELETE /api/v1/me with the owner credential |

Better Auth applies its own per-IP limits to `/api/auth` routes, for example 3 sign-in attempts per 10 seconds, and returns 429 with `X-Retry-After`. The owner principal is not subject to account quotas or share rate limits.

## Checks

`npm run check` regenerates binding types, builds the browser auth client into `public/app/` (generated, not committed), typechecks, tests real R2 multipart/range/authorization/revocation behavior, account isolation, device flow, quotas, signup gate, rate limits and account deletion, and packages a deployment dry run. `worker-configuration.d.ts` is generated, never edited manually. Native CI checks the shared Rust client, desktop and CLI and builds an isolated macOS preview.
